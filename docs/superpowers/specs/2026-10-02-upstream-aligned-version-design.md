# Nofy 上游对齐版本机制

日期：2026-10-02。用户已同意暂用“上游基线 + Nofy 修订号”方案。

## 目标与范围

让用户通过 CLI 版本信息识别已审计吸收的上游基线、Nofy 修订及构建时的源码状态。
修改 Rust 内核的版本生成、共享版本信息和用户可见版本显示；不修改桌面应用版本、
不引入上游云端更新、渠道查询或遥测，不重编号所有内部 crate。

## 格式与含义

示例（本地提交为占位展示，不是固定值）：

```text
nofy 1.0.45+nofy.1 (<local-commit>, dirty)
upstream 1.0.45 (2bdd1d6a6369)
```

- `1.0.45` 是已完成审计吸收的上游发布基线。
- `+nofy.1` 是 Nofy 修订标识，保持合法 SemVer；后续本地发布递增修订号。
- 本地 commit 取构建仓库 HEAD 的前 12 个字符；工作区有未提交改动时附加 `dirty`，干净时省略。
- 上游 commit 固定记录为 `2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8`，显示前 12 个字符。
- `dirty` 来自构建时 Git 状态，包含已跟踪改动及未忽略的未跟踪文件，不是启动时实时状态。
- SemVer build metadata 不参与版本优先级比较；不能用 `nofy.1` 与 `nofy.2` 的普通 SemVer
  排序判断哪个修订更新。本次不新增自动更新排序机制。

## 实现边界

以共享版本模块为统一读取入口，产品版本与组成根二进制包保持一致。
上游基线版本和提交使用可审查的仓库内元数据保存，不通过 Git merge-base 推断：
原生移植并不意味着上游 commit 已成为本地祖先。

保留 `NOFY_VERSION` 发布构建覆盖入口和 `NOFY_TEST_VERSION` 测试入口；发布覆盖值须为合法 SemVer，
不能隐式更改已记录的上游吸收基线。机器使用的版本字段保持单一 SemVer，不能混入第二行或 `dirty`。
共享完整版本采用上游的二进制构建时注入方式，避免每次 HEAD 变化触发全部库重编译。
用户可见 `--version` 输出显示本地完整版本和上游基线；界面按布局使用共享格式化入口，
协议上报保持兼容且版本来源一致。

吸收上游的 Git 路径解析方式，正确处理普通 checkout、worktree、分离 HEAD 和分支 ref 更新。
构建依赖监听必须覆盖版本元数据、发布覆盖变量以及提交/源码状态变化，验证增量构建不残留旧标记。
Git 不可用或源码归档构建时显示 `unknown`，无法读取工作区状态时不能伪装成已确认的 clean。
元数据格式错误应给出明确构建诊断，不静默写入假的上游版本。

## 基线更新流程

fetch 上游不自动提升版本。只有完成一轮吸收/差异审计后，才同步更新基线版本、基线提交和台账。
基线表示审计吸收进度，不承诺与上游逐行相同，也不证明缺陷全部消除。
需要最新差距时仍须 fetch 并比较上游发布与审计记录；离线 `--version` 不猜测远端进度。

## 验证与交付

覆盖版本格式、SemVer 解析、clean/dirty/unknown、发布覆盖、共享注入及 Git 路径场景。
检查实际 `--version`、界面版本和机器字段的一致性；每个现有符号修改前执行 GitNexus impact。
提交前执行 detect_changes，只纳入本任务文件，不带入已有内核/桌面脏工作区。
验证阶段控制构建缓存体积，不跑无关全库测试。若安装新二进制，校验默认 `nofy` 路径及启动结果；
未重建安装前明确现有命令仍为旧版本机制，不能声称实现已生效。

## 方案取舍与当前状态

独立 `0.2.x` 编号不直观反映上游基线；完全照抄 `1.0.45` 又隐藏二次开发身份。
因此暂用 `1.0.45+nofy.1`，将发布基线、Nofy 修订及源码身份分开显示。
本文件仅确立设计，代码尚未修改，待用户审阅后进入实现计划。

# Rust/CLI 版本与发布链补齐

日期：2026-10-15。状态：用户已确认，Rust/CLI 实现已落地；本机原生验证，远端 CI/其他平台未执行。本设计承接已落地的上游对齐版本机制。

## 目标与边界

补齐从升版、构建、机器查询、修订号比较到本地产物与发布校验的链路。仅涉及 Rust/CLI；不修改桌面端，不引入遥测、云端版本查询或自动下载安装。实施、测试不包含 push、远程 tag 或公开 Release 发布。

## 方案取舍

采用仓库内 Rust 发布工具与 CI 校验，复用已有版本格式和共享版本规则。相比只加几个升版脚本，它能统一比较、校验及产物契约；相比接入远程自动更新，它不需要新增账号、服务或安装来源信任机制。保持 `1.0.45+nofy.N`，不改成会改变 SemVer 稳定版含义的 prerelease 格式。

## 1. 统一元数据和升版入口

- `crates/codegen/nofy-version/upstream-version.txt` 继续记录上游版本、完整上游提交、Nofy 修订；不因 fetch 自动提升。
- 新增独立的内部工具包 `nofy-release`，不依赖会在构建期校验产品版本的 `nofy-version` 库，以免版本不一致时连修复工具也无法启动。共享纯版本解析/比较源文件，避免两套规则。
- 入口为 `cargo run --locked -p nofy-release -- <command>`。`check` 只读校验；`bump revision` 自动递增 Nofy 修订；`bump baseline --version V --commit SHA` 显式更换已审计的基线。上游版本提高时修订重置为 1，同版本更换 SHA 时递增修订，版本与 SHA 均相同则拒绝空操作。
- 升版同步修改元数据、`nofy-version` 与 `nofy-pager-bin` 的 Cargo 包版本及 Cargo.lock 中这两个本地包版本。不重编号内部 crate，不重新解析整个依赖图，不改变其他锁定依赖。
- 默认预览变更，只有 `--apply` 才写入。拒绝元数据非法、原版本漂移、基线倒退、发行记录中的重复版本及修订溢出。上游 SHA 必须完整，校验本地目标提交存在，并核对其上游产品包版本与 V 一致；无法验证时不假装已完成审计。该机械校验不代替功能吸收审计。
- 写入前读取并验证所有目标；保留不相关脏改动与文件内容。逐文件临时写入后替换，失败时尝试恢复本次已写文件并明确报告；不承诺跨文件断电原子性。重新 `check` 能发现中途不一致。

## 2. 机器版本与展示版本分离

- `nofy --version` 保持现有两行人读输出。
- `nofy version --json` 保留 `currentVersion` 字段名，但将值修正为单一合法 SemVer；另提供 `fullVersion` 展示串。
- JSON 同时提供 `schemaVersion`、上游版本/完整 SHA、本地构建 SHA、工作区状态（clean/dirty/unknown）和编译 target。
- 对既有调用方进行检索并补回归；版本策略、协议客户端版本继续使用共享 SemVer，不把两行文本或 dirty 注入机器版本。
- 缺失 Git 时 SHA/状态明确为 unknown，不伪装成干净发布；所有字段都来自编译时元数据，不把启动时 HEAD 当成构建身份。
- CLI JSON 不要求用户配置模型、不启动会话、不连接后台服务，作为发布工具检查二进制身份的稳定入口。

## 3. Nofy 版本比较

- 先按 SemVer precedence 比较基础版本（包含预发布规则），相同后按 `nofy.N` 的整数修订比较，禁止字符串字典序。
- `1.0.45+nofy.10` 高于 `1.0.45+nofy.2`；`1.0.46+nofy.1` 高于 `1.0.45+nofy.999`；不同 Git SHA 或 dirty 标记不决定发行版本先后。
- 无 build metadata 的合法旧版本按修订 0 处理；非 `nofy.N` 的不明确 build metadata 返回不支持错误，不自行猜测顺序。
- 对外提供 `compare CURRENT CANDIDATE`，明确输出 newer/equal/older，并保持稳定退出约定；发布工具实际使用同一比较规则拒绝回退，而不是只提供一个无人调用的函数。
- 不把发行版比较规则强行替换配置中的标准 SemVer 范围匹配，不改变信任、安全策略或协议兼容范围语义。

## 4. 构建、产物和安装闭环

- `package` 在构建前执行一致性校验；构建后读取该二进制的 JSON 身份，核对产品版本、上游基线与实际编译 target。不能仅按文件名判断版本。
- 正式包要求 clean Git 状态且构建 SHA 与当前提交一致；当前脏工作区只能显式选择 `--snapshot --allow-dirty`，产物必须标记非正式快照，不清理、不暂存或提交用户已有改动。
- 使用明确的新输出目录，默认拒绝覆盖既有产物。产物名包含产品版本和 target；快照额外带短 SHA/状态，避免与正式包混淆。
- 产物附带有 schema 版本的 JSON 清单、SHA-256、文件大小、产品版本、基线、构建身份、target 和快照标识；不嵌入凭据或本机完整路径。
- `verify` 实际检查清单、哈希和产物身份；拒绝文件损坏、错误 target、版本不符和正式包中的 dirty/unknown。
- 本机 `install` 显式选择产物并先 verify，默认拒绝降级，同版本也需要显式 reinstall；备份旧二进制，原子替换，执行安装后 JSON 及哈希校验，失败则恢复旧二进制。不终止用户正在运行的旧进程。
- 工具具备本地闭环，不默认拉取网络发布源或在启动时自更新。正式签名、远端发布渠道与凭据不在本次授权范围。

## 5. CI 与发布记录

- 新增独立 CLI workflow，与现有桌面 workflow 隔离。运行元数据/比较/升版临时仓库测试、CLI JSON 契约测试，执行原生构建和产物 verify。
- 升版工具更新独立 CLI 发行记录，至少记录原/新产品版本、对应上游基线和提交；变更说明由实际改动提供，不能自动编造“已全部吸收”。
- 正式打包执行发行记录一致性校验；默认不替用户创建 tag、推送分支或公开 Release。
- CI 配置只说明预期平台覆盖。交付中分别报告本机已执行验证和未执行的远端/其他平台验证，不以配置存在冒充 CI 已通过。

## 验收

1. 临时 Git 仓库验证升版预览零写入、实际升版四处一致、保留无关脏改动、错误时不产生静默半成品，并通过 Cargo locked 校验。
2. 比较覆盖 revision 2/10、基线变化、相等、旧版本、预发布、无效 metadata 和溢出；至少一个打包/安装拒绝回退路径调用比较器。
3. 真实 `nofy version --json` 的 `currentVersion` 可被 SemVer 解析，构建 SHA/状态与 `--version` 一致；无配置环境也可查询，不创建会话或等待服务。
4. 验证打包→清单→哈希→verify→隔离安装→重查版本；篡改、错误版本/target、dirty 正式包、降级及安装校验失败均有负向测试。
5. 正式发布拒绝当前脏工作区是预期行为；以临时干净仓库完成正式门禁测试，不为测试清理用户仓库。
6. GitNexus impact 在现有符号编辑前执行，HIGH/CRITICAL 先告知；提交前 detect_changes，只提交本任务变更。使用低缓存构建参数，不做整库格式化或无关全库测试。
7. 完成后更新现有版本设计的状态及边界；桌面目录与配置无本任务改动。

## 实施说明

使用独立 `nofy-release` 工具，操作命令与信任边界见 `docs/cli-release.md`。
本批由工具将产品修订升至 `1.0.45+nofy.2`，上游基线与 SHA 未提升；没有借版本升号宣称 TUI 已吸收。
原生回归包含真实二进制 JSON 查询、隔离快照打包/验证/安装；正式 clean 门禁、升版与失败回滚使用临时 Git 仓库测试。
本机脏工作区仅生成显式快照，没有创建正式发行、远程 tag、推送或公开 Release。

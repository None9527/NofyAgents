# 全平台计划：Linux、macOS、Windows，以及桌面版

目标：同一个内核在三个平台上运行，并为后续桌面版提供可内嵌的服务。本文记录第一性原理下的约束、实测的移植面、阶段与验收标准，以及一个必须由人决定的架构选择。

## 第一性原理：什么必须在各平台一致

1. **契约与状态语义一致。** 97 项操作、持久回执、恢复、预算、审批在任何平台上含义相同；契约不因平台而分叉。
2. **隔离只能失败关闭，不能悄悄变弱。** 模块声明它需要的约束（文件范围、无网络、不可派生进程）。平台实际强制不了某项约束时，内核拒绝运行该模块，并报告缺哪一项；不允许降级后继续运行。`--probe` 报告的强制事实是唯一依据，不看平台名。
3. **持久化语义逐平台验证。** 恢复依赖 fsync、原子重命名和文件锁；这些在 Windows 与 macOS 上语义不同（Windows 没有目录 fsync，重命名遇到已打开的文件会失败；macOS 的 `fsync` 默认不落盘，需要 `F_FULLFSYNC`）。现有的真实杀进程恢复测试必须在每个平台上跑。

## 实测的移植面

下面的计数是正则命中数（`libc::`、`nix::`、`landlock`、`cgroup`、`seccomp`、`SYS_*`、`std::os::unix|fd`），用来衡量集中度，不是需要改写的行数。

| 事实 | 数值 |
|---|---|
| 包总数 | 22 |
| 完全没有平台相关代码的包 | 12 |
| `nofy-agent-runtime`（持久化运行时，4.2 万行） | 0 处 `libc::`，几乎已可移植 |
| `nofy-agent-host`（2.5 万行） | 557 处 `libc::`，132 处 seccomp/syscall，87 处 cgroup |
| host 平台命中的去向 | `loader/process_tree` 49%，`loader` 顶层隔离文件 36%，`loader/process_sessions` 10%，合计约 96% |
| host 中没有任何平台代码的部分 | HTTP API、认证、会话与记忆接口、源码仓库、运行历史、作用域、提示渲染 |
| 已有的非 Linux 起点 | `nofy-tty-utils`（Windows 15 处、macOS 5 处条件编译） |

结论：难点是**一层**，即进程隔离（进程树监督与资源限制、文件与网络约束、终端、fd 传递）。其余部分要么已可移植，要么只需要验证。

Linux 专有的功能在其他平台上没有对应物，需要明确标为"不支持"，而不是移植：锁定的 glibc 运行时镜像（ELF64）。用户自备环境（`resource.process_local`）是跨平台路径。

## 目标架构

在 host 内围绕隔离层划一条边界：

- 一组能力：`confine_filesystem`、`deny_network`、`deny_process_spawn`、`limit_resources`、`supervise_process_tree`、`terminal`。
- 一个探针：每个后端如实报告自己强制了哪几项。
- 一个策略：模块声明的需求超出探针结果时拒绝，错误码 `isolation_unavailable`，信息里写明缺哪一项。
- Linux 后端就是现有代码，**搬到边界后面，不改行为**；已有的全部测试不变，就是这次重构的验收。

## 阶段与验收

| 阶段 | 内容 | 验收 |
|---|---|---|
| S0 测量 | CI 在 macOS 与 Windows 上原生编译，得到逐包错误清单 | 有每个平台逐包的错误数 |
| S1 可移植层 | 命令行、MCP 桥、客户端、工程引擎在两个平台构建并测试；决定 Windows 令牌文件的 ACL 检查 | `client-portability` 在两个平台全绿 |
| S2 隔离边界 | 接口与准入已落地（`nofy-isolation`，见[沙箱模块化](sandbox-module.md)）；Linux 后端适配；其他平台返回"不支持" | host 在 macOS 与 Windows 上编译；Linux 闸门与全部测试不变 |
| S3 控制面全平台 | 内核在三个平台启动并提供项目、草稿、系统、会话接口；需要隔离的执行以 `isolation_unavailable` 拒绝 | 不需要隔离的测试在三个平台上通过 |
| S4 隔离后端 | 每个平台原生实现，部分改造自参考项目，见[沙箱模块化](sandbox-module.md) | 每个后端通过同一组验收：探针事实、`process_tree` 一类的真实杀进程与取消测试 |
| S5 桌面版 | 内核作为随应用分发的服务；安装包、签名、更新 | 桌面应用端到端运行一个 Agent |

S0 到 S3 现在就可以做。

## 已决定：每个平台原生隔离，不用虚拟机

曾经考虑过两个方案：桌面版自带 Linux 虚拟机来复用现有隔离，或每个平台各自实现原生隔离。**已决定不采用虚拟机**，每个平台使用原生机制：macOS 用 Seatbelt，Windows 用受限令牌、作业对象与 ACL。代价是三套各自需要审计的安全实现，所以隔离被做成可替换的模块，并允许改造参考项目中已有的实现，见[沙箱模块化](sandbox-module.md)。

## 风险

- 隔离是安全边界。任何后端都必须有对抗性验收，不能只验证"功能能跑"。
- macOS 与 Windows 的 CI 分钟数更贵，真实杀进程测试更慢；需要为这些平台拆分测试集。
- 路径语义（盘符、大小写不敏感、保留名、符号链接）会影响源码包规范化与 `resource.process_local` 的绝对路径约定。

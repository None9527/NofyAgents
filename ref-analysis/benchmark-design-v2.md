# Nofy 能力基准设计 v2 —— 按真实用户使用标定

> 日期:2026-08-21 · 取代:`benchmark-design.md`(v1,按代码结构标定)
> 重梳动机:v1 的维度是**架构接缝**(项目入口/全局入口/控制面/FR 域)——那是开发者眼里的产品。用户眼里没有接缝:用户只有**一份配置、几个项目、把活交出去、回来收结果**。基准必须站在用户这一侧,测「用户的活干成了没有」,而不是「代码通道是否连通」。

---

## 0. v1 的问题(为什么重梳)

1. **维度按代码切**:D5/D6/D7 对应的是三条执行通道的接线,用户从不感知「通道」;
2. **驱动面靠内**:部分题目用控制面客户端(socket 帧)驱动——那是诊断工具,不是用户界面;
3. **配置假设分散**:v1 各题各自注入环境变量/旗标,而真实用户**只在一个地方配置模型**;
4. **判据偏机制**:「journal 出现某事件」是机制证据,不是用户证据。用户只认**产物与行为**。

## 1. v2 标定原则

1. **用户面唯一驱动**:每题只能从用户真实接触的界面发起——**配置文件**(`~/.nofy/config.toml`,即用户说的「那个 config」)、**命令行**(`nofy`/`nofy -p`/`nofy schedule`/`nofy sessions`)、**项目目录里的文件**。socket/journal 等内部观察面**只允许用于失败归因,不允许作为驱动或判分依据**。
2. **一份配置是一等测试对象**:用户关于模型的全部知识 = 一个文件里的一段。所有入口(交互会话、headless、调度任务、委派任务)必须从这同一处取模型。**「单配置属性」是门级测试**(U1-05),任何入口绕过它 = 基准失败。
3. **结果判据 = 用户可验证的产物**:文件及其内容、测试绿、命令输出、日程是否触发、审批是否弹出。模型「说自己做了」永远不算。
4. **归因三槽保留**(M 模型 / W 产品 / H 基准),但归因时才允许打开内部观察面。
5. **pass@1 记分,失败重跑 2 次记 pass@3**,区分「不会」与「不稳」。

## 2. 用户画像与环境

**画像**:一名开发者,管理 2 个工作项目 + 1 个文档堆;用自己的模型端点(BYOK);日常:在项目里写代码、把杂活交给助手、定时跑重复任务、偶尔跨项目找东西。

**环境**(复用 v1 harness 的 fixture,驱动面全部换成用户面):

| 物件 | 内容 |
|---|---|
| 配置文件 | `$NOFY_HOME/config.toml`——**唯一**模型/偏好配置点:`[models] default` + `[model.bench]`(base_url + env_key 指 key) |
| 项目 alpha | Python 库:含隐藏 bug 的测试、AGENTS.md 约定(改完跑 pytest)、README 中文约定(提交信息中文) |
| 项目 beta | Shell 工具项目:硬编码路径脚本、中文文档 |
| 文档堆 gamma | 中英混杂文档 + 重复文件 + 大文件 |
| 模型 | deepseek-v4-flash-0731(DashScope 兼容端点),key 经 env_key 引用不落盘 |

## 4. 单配置属性:门级测试(U1-05 展开)

用户的断言:**「配置模型只有一个地方」**。基准把它做成显式门:

```
同一份 config.toml(一个模型段)
  ├─ 交互会话(TUI/ACP)实际所用模型
  ├─ headless -p 实际所用模型
  ├─ 委派任务(provider)实际所用模型
  └─ 定时触发的任务实际所用模型
四者必须一致;任一不一致 = 门失败(归 W)。
```

验证手段(用户面):会话记录中的模型字段 / 任务产物带模型指纹(让模型自报身份+端点特征核对)。内部解析路径只在归因时看。

> 历史对照:v1 期间发现并修复的两条双线(provider 绕 config、headless 丢旗标)正是本门要永久守住的东西——v2 把它从「事后发现」变成「每次跑都验」。

## 6. 评分与报告

- **维度分** = 该维 10 题 pass@1 通过率;**总分** = 十维平均(U1-05 单配置门为**否决项**:不过则总分标记「配置一致性未达标」)。
- **报告**:十维雷达 + 逐题明细 + 归因分布 + 与上次运行 diff;所有失败题附用户面复现命令。
- **模型对照**:同一题集换模型重跑即得横评(U10-02 是 harness 能力,不是单题)。
